# Private export source inventory

The private snapshot builder now reads dataset counts and optional-table availability once for its single read-only repeatable-read source transaction. It skips each empty or exhausted dataset independently. The ordinary `GET /export` route keeps its signature and delegates to the same internal page builder without an inventory. There is one projection implementation, with the same fields, ordering, dataset keys, totals and page format.

`SnapshotSourceContext.prepare` reads only scalar inventory. It binds the exact source session, live transaction, stable owner and enrollment generation. It refuses a writable/read-committed source or reuse under another owner, generation, session or transaction. The normal PostgreSQL size guard still runs on every page, including the profile reserve. The first guard must succeed before any profile JSON or static source metadata is loaded. Static metadata is retained as an immutable JSON string and returned as independent copies.

The service records its built-in/custom source choice at construction. Replacing the callback with an await-preserving wrapper later does not disable inventory. Each callback still receives four arguments; a private per-call ContextVar carries the typed source context to the built-in callback and is reset in `finally`. Custom callbacks explicitly receive no inventory context, even when their caller has an ambient context. The ordinary export route never reads that ContextVar. Providers receive an explicit optional typed context and validate its scope and guarded page before queries.

Optional groups preserve their individual paging behavior: health connections can be exhausted while observations continue; collection metadata does not suppress members; a singleton Recipes epoch appears only on its original slice. Content-free import allowance receipts keep their existing owner-only, cross-generation semantics. Profile readiness and measurement current-selection projections are unchanged; no new readiness dataset is introduced. A 034-only schema continues to omit the same unavailable optional groups.

The context and raw page references are retired inside the source-session scope before rollback or exceptional exit releases the global build lock. This includes cancellation. Counts/table names can remain as small scalar metadata, but retained private JSON is cleared and the context rejects further use.

Writer and reader privacy checks remain fresh. Inventory is never passed to `_write_page`, manifest publication, `privacy_digest`, snapshot reads or invalidation. Current membership, permission epoch, clock and owner locks are still checked before each page commit and final ready publication. Existing encryption, 8 MiB page/64 MiB total bounds, 10-record pages, 512-page limit, 120-second build deadline and ten-minute expiry remain.

## Verification and limits

The new real-PostgreSQL tests compare optimized and legacy page output across core and optional datasets, independently exhausted groups and empty pages; preserve 190 workouts and 190 full versions; reject wrong scope/transaction reuse; prove scalar inventory and guard-before-profile loading; preserve a fixed source view across ordinary concurrent additions/edits; isolate concurrent legacy exports; retain custom/wrapped callback behavior; and clear context on success, failure and cancellation. A built-in cached-metadata race invalidates privacy after the first committed page and verifies that the fresh next writer cannot publish it.

For a representative 190-record/190-version, 19-page source fixture, ordinary projection used **1,014 queries**. Optimized source preparation plus all projections and all page size guards used **324 queries**, about 68% fewer. The fixture uses synthetic prescription data; this is a query-count regression, not a latency benchmark or the large-payload hosted capacity workload.

Testing uses the unchanged pinned production dependency versions on local macOS ARM Python 3.12.8 with a disposable PostgreSQL 16 fixture. It does not establish Linux x86/0.5 CPU/512 MiB, Render/Neon, provider or native acceptance. The previous hosted export latency and broader capacity gates remain failed until root reviews and tests the final combined candidate. No one-second latency promise, deployment, configuration enablement, async contract or new infrastructure is included.
