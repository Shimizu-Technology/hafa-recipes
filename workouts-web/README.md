# Håfa Workouts website

Independent static marketing, support, privacy, deletion, terms and intentional public sharing website. The Recipes website is untouched. iPhone/Android beta links are explicitly pending.

Node 22.22.3: `npm ci`, `npm run check`. `npm run dev` is a local runtime; claim and clean it through the lifecycle skill. Build emits `dist/` with prerendered public pages and a generated strict CSP `_headers`. Tests use synthetic public projections and make no live API/provider request.

Set `VITE_WORKOUTS_PUBLIC_API_BASE` to the selected verified HTTPS API origin before build. Empty config keeps the public website usable but disables snapshot reading. Never put an API key, Clerk secret, access token or private service URL in a VITE variable. Preview and production must have deliberately selected API origins and matching CORS; no production default exists.

Use `netlify.toml` only on an independent Workouts site. Configure the base as `workouts-web`, publish `dist`, and verify generated CSP/referrer/cache/robots headers on a Deploy Preview. No site/domain was provisioned by this implementation. The main release task owns deployment, final policies and install links.

Preferred web share links use `/shared#token`. Existing `/shared/token` works and is scrubbed to the fragment in browser history. No client telemetry, referrer, storage or automatically sent mail/import is added. Hosting/API access logs require separate redaction/retention verification; a browser cannot erase a legacy token path that hosting already received.

See [website brief and QA ledger](../docs/hafa-workouts/WEBSITE.md) for source attribution, security bounds, exact dependency decisions and actual interaction/release gates.

Local public-preview QA can use `VITE_WORKOUTS_PUBLIC_API_BASE=http://127.0.0.1:8088 npm run dev -- --port 5182` from this directory, with the API's CORS explicitly allowing the selected website origin. Vite serve already supported localhost/127.0.0.1 HTTP before this follow-up; validation now also supports literal `[::1]` and rejects numeric aliases, hostname lookalikes, credentials, paths, queries and fragments. Only Vite's compile-time development **serve** mode permits HTTP. Every build remains HTTPS-only, including a build with `NODE_ENV=development`; a runtime boolean, URL parameter or VITE flag cannot enable it. No TLS interstitial/CA workaround is needed for the owned synthetic loopback service.

The dev-only CSP permits self, the exact configured API origin and `ws://127.0.0.1:<actual Vite port>` for HMR. Its inline script/style allowance is limited to Vite serve for React Refresh/CSS updates. Generated production CSP remains unchanged: no unsafe-inline, wildcard connection or websocket allowance. HMR is pinned to 127.0.0.1 rather than trusting the request Host header. Actual browser CSP/HMR/CORS and shared-preview happy-path CUA remain **not run** in this slice; root owns that acceptance and runtime cleanup.

Dependency recheck on Node 22.22.3/npm 10.9.8: the checked-in lock installs with `npm ci --legacy-peer-deps=false --strict-peer-deps --no-audit --no-fund`, and `npm ls --all` reports no active peer conflict. Fresh lock generation from the same manifest using `npm install --package-lock-only --legacy-peer-deps=false --ignore-scripts --no-audit --no-fund` reproduces npm Arborist's `Cannot read properties of null (reading 'edgesOut')` in `#loadPeerSet`, while expanding optional Vite devtools adapters. Vite 8.2.1 declares optional `@vitejs/devtools ^0.4.0`; those tools are absent from the active locked application graph. This is a resolver failure rather than evidence that the pinned Vite8/plugin-react6/Vitest4/React19 active pairs are incompatible. The existing `.npmrc` workaround is retained for fresh resolution; `legacy-peer-deps` ignores **all** peer resolution, so use the strict locked-install check when changing dependencies. No dependency major, manifest, lock or shared CI was changed.

Source gate: typecheck, 38 tests, client/SSR/prerender build passed. Compiled SSR rejects all three loopback HTTP spellings even with an obsolete runtime opt-in argument, and the same check passed for build command with NODE_ENV=development. A synthetic HTTPS-origin build generated exactly that connect-src origin without dev allowances. Temporary peer-resolution fixtures were removed. No server, browser, container, native runtime, production data or AI provider call was used; the clean isolated worktree is preserved for root integration.
